# 内容维护和自动更新约定

本文供项目维护者和自动更新任务使用，访客请阅读仓库根目录 README。

## 收录范围

- 包括官方 AI 模型厂商、推理平台、开发者 AI API 福利、可核实的非营利公益 API 服务。
- 不收录普通商业中转站的充值赠送、倍率优惠或促销信息。
- 禁止未经核实地把老活动描述为当前可领取。

## 鸡蛋数据

编辑 `data/eggs.json` 的 `eggs` 数组，每个对象建议提供：

- `id`: 不变的机器标识。
- `name`, `description`, `type`: 展示名、简介、来源类型。
- `status`: `pending`（待核实）、`active`（已核实有效）、`expired`（已失效）。
- `credits`: 金额 / 免费额度，说明是否要求充值或绑定卡。
- `models`: 可使用的具体模型名称数组，未知时标记待核实。
- `requirements`: 注册和领取门槛（地域、手机号、卡、邮箱、企业身份等）。
- `discovered_at`: 第一次发现该线索的时间；不要把随意整理时间伪装为发现时间。
- `verified_at`: 最近验证的时间，未知用 null。
- `verification_note`: 证据、查验方法以及存疑信息。
- `url`: 最好指向官方活动页面，不要贴无法证实的跳转。

更严格的收录建议逐步引入 `evidence_urls`、`expired_at`、`expiration_reason`、`last_seen_at` 等字段。

## 核实标准

1. 尽量找到官方活动页、定价页、文档或公开公告，避免仅凭二手转述。
2. 检查是否仍能申请，关注地区、绑卡、企业 / 学生认证、有效期与额度归零条件。
3. 没有足够证据时保持 `pending`。只有当当前活动与门槛有可验证来源时才设 `active`。
4. 查到活动结束时改为 `expired`，保留原有记录并补充原因。
5. 每次更新数据或报告都要保持 JSON 格式有效，并附来源。
6. 不应在网站暴露 API Key、邀请码私密凭证、账号信息。

## 早晚报

`data/reports.json` 包含 `morning` 与 `evening`：

- **早报**：轻快、元气、信息密集，重点讲新发现和当天优先领取的高价值项目。
- **晚报**：稍显抽象、吐槽式复盘，但信息准确，重点讲状态变化、失效和踩坑。
- 每条至少包含 `date`、`title`、`summary`。若没有最新可验证内容，就如实说明无更新，不得伪造每日新闻。

## 历史小报与超级鸡蛋报（不可覆盖往期）

- `data/reports.json` 只存当前展示的最新早报和晚报，作为首页摘要缓存；完整历史维护在 `data/report-archive.json` 的 `entries` 数组中。
- 每天北京时间 **08:00** 形成一份 `kind:"morning"`，每天 **19:00** 形成一份 `kind:"evening"`。每次先检查相同 `kind` 和 `date` 是否存在；若当天修订，仅更新当日对应条目；不同日期的已发布记录不得被覆盖或删除。
- 历史条目有稳定 `id`（如 `2026-10-08-morning`、`2026-10-08-evening`），`kind` 为 `morning` / `evening` / `super`，还包括 `date`、`title`、`summary`、`highlights`（字符串数组）和 `tip`。
- 晚报未到发布时间、任务失败或没有成功发布时，**不得生成带日期的假记录**。页面仍可显示“等待出刊”，历史区只展示真实存在的条目。
- `kind:"super"` 为独立的超级鸡蛋专题，发现真正的新高价值活动时写入，并附 `egg_id`、`official_source_url`、`claim_url`；对同一活动去重，后续活动失效时更新专题状态信息，不能继续暗示仍能领取。
- 发布历史后检查首页 latest 与历史同一期内容一致；时间、首发、修订都按实际记录，不把旧事件改写成当天新发现。

## 待核实任务必须每天关闭循环

1. **每日必查每颗 pending**：至少一次逐项核对官方专属活动页、领取资格、额度、支持模型、地区、绑卡/充值门槛及有效期。记录 `last_reviewed_at`、`next_review_at`、`review_history`，写清哪条来源验证了什么、仍缺什么；只有实际调查才算一次尝试。同一天多次运行不能凑核查天数。
2. 发现当期有效依据且可领取 -> `active` + 分级；查证活动结束 -> `expired`；查明活动需要不符合收录范围的资质（如特定企业申请）-> `excluded`，不可假称已失效。
3. **连续 3 个不同自然日核查仍缺乏可信的当前领取证据** -> `unverifiable`，转到核查归档、从公开默认列表和待核实列表退出；不意味着历史活动确定结束。保留原始链接、核查证据和 `review_result` 以便追踪。若新官方证据出现，可重新打开。
4. `unverifiable` 和 `excluded` 不属于有效等级，不参与超级/优质/普通排序；网页的“核查归档”可查询，已失效永远放在最后。
5. 审查某一特定活动时区分其他产品免费档，不能因为一个企业专项被排除就排除同一平台对个人开放的不同免费服务。

## 文案风格（Eku 免费鸡蛋主题）

- **像真人写短评，不套格式**：先说最有意思或最实用的事实，1～2 句足够；有梗则用，没有就直说。不同鸡蛋不用同一种开头，也无需每条都强行提“鸡蛋”“香”“冲”。避免“等一下居然……！不过……”“看着很大，但……”“先别……”“这不等于……”“具体以……为准”等反复出现的 AI 口吻。
- **可爱不等于编故事**：不杜撰体验、当天刚上线、测试成功、已经到账、官方保证、即将失效；无法验证继续写“待核实”。数额不可以把不同活动或不同档位相加。
- **统一网站免责声明只放页脚**：如“信息来源于公开资料”“实际以官方规则为准”等通用说明仅写在页面底部的「信息来源与免责声明」中，不在每张鸡蛋卡片、日报或等级理由后反复添加；具体活动的绑卡、额度、时限仍需在活动字段明确展示。
- **说一次就够了**：`description` 只讲核心优点和会改变用户决定的限制，不要在结尾额外加一句泛泛的风险提示、免责声明或同义复述。例如“可免费调用，有限速”后不要再写“想一直用还得看正式额度”。真实条件分别写入 `credits`、`models`、`requirements`、`payment_required`、`verification_note`、`status`、`grade` 等字段；`grade_reason` 只说为什么评这个等级，不能重复整段描述或把注意事项再念一遍。用户需要更多细节时能看字段和官方来源。
- **早报**：轻松、元气、有一点 Eku 表情包式幽默，但别每条消息都加俏皮铺垫。用简短开场与 2～4 条重点（highlights）讲清新发现、变更和可领取活动；`tip` 仅当有新的具体实用建议时填写，否则留空。避免机械地每条最后加一句提醒。
- **晚报**：轻微抽象、允许自然吐槽，重点复盘当天新增、失效、门槛变化和核实结果。不开玩笑也没关系，优先读起来顺口；没有变化就简短说明，不用生硬套梗。`tip` 可以为空。
- **真实时间**：只写已经核实并发布的信息，尚未出刊要留 `date:null`；日报只可报道可追踪变化，不要把历史整理假装成今天发生。
- 禁止直接复制第三方表情包文案、恶意攻击平台、贬低使用者；网站整体保持可爱、清爽、略抽象的语气。


## 文案检查清单

发布前通读每个 `description`、`grade_reason`、早晚报：是否重复警告已经说明过的限速/绑卡/模型限制？是否每段都在收尾加“但、不过、不等于、以实际为准”？是否重复表演惊讶或用“先别”指挥读者？有就删掉赘句或把必要的条件放回字段。**核心是事实清楚、语气自然，俏皮只做点缀。**

## 投稿流程

用户提交 GitHub Issue 后先核实，再由维护者合并到 JSON；公开投稿内容不应该直接写入“有效”列表。

## 发布机制

当前为静态 HTML + JSON，Cloudflare Pages 与 Vercel 均可托管。绑定 Git 后向默认分支提交即可触发构建。自动任务能否在无人值守时使用 ChatGPT 的 GitHub 写权限，需要单独验证，不能因普通会话写入成功就默认定时运行也能写入。
